# Isolated Hub staging

Use a dedicated, empty managed Supabase project and a separate static preview deployment. The static bundle builder works with Cloudflare Pages Direct Upload or a separate GitHub Pages repository. A direct-upload site avoids a GitHub-hosted build. Public hosting is suitable only for the static bundle and synthetic accounts. Keep all classroom data out. On GitHub Pages use a different owner or hostname, since the builder deliberately rejects the production GitHub Pages hostname to avoid sharing browser storage.

The existing Supabase Free organisation has two active projects and two inactive projects. The active pair fills the Free quota. A new paid organisation with one Micro project starts at the published Pro rate of $25/month before applicable taxes or excess usage. Upgrading the existing organisation would also move the active projects into its billing model. Preview branching requires a paid plan, with separately metered compute and usage. Free projects can pause after a week of inactivity. Verify the account-specific quote and get approval before provisioning. Do not pause or repurpose an existing project as part of staging setup.

Official references: [billing and free project quota](https://supabase.com/docs/guides/platform/billing-on-supabase), [pricing](https://supabase.com/pricing), [branch usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching), [Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

## Build and publish

1. Fetch the intended feature branch into a dedicated checkout. Pin its exact commit. Confirm the assigned staging Supabase reference is distinct from production and belongs to the approved empty project. Verify its key in the staging dashboard. Use a publishable key here and keep all secret/service keys server-side.
2. Reserve a distinct frontend origin and choose the precise base URL with a trailing slash. If using Cloudflare, upload the static output to a separate Direct Upload project. Serve HTTPS for managed tests. A loopback URL is available for a local frontend smoke.
3. Set `HUB_STAGING_SUPABASE_REF`, `HUB_STAGING_PUBLISHABLE_KEY`, and `HUB_STAGING_SITE_URL` in the staging build environment. Build to a fresh directory outside the repository with `node scripts/build-staging.mjs /path/to/new-output <commit>`. Upload only this directory. Keep `HUB_STAGING_ACTIVE_TIME` and `HUB_STAGING_MICROSOFT` unset for the first build.
4. Verify `staging-build.json`, the banner, the displayed URL, the Auth callback, an ordinary password login, and browser network traffic. The bundle rewrites the browser configuration, individual module launches and Microsoft callback. It rejects the production project reference, live key and production Pages hostname. Its CSP limits connection destinations to the staging Supabase host and blocks embedded frames. The externally hosted Reading, Listening, Paraphrasing and Essay modules are intentionally omitted from the staging launcher because those embeds may be served by live applications. The production source code and production deployment are unaffected.
5. For later tests rebuild from the intended commit. Only a staging bundle sets either optional browser gate to true through the corresponding explicit environment variable. Keep the production branch gates unchanged.

## Bootstrap a fresh database

Use a staging-only CLI checkout or the management connector with the staging reference explicitly selected. Verify the reference in every migration and function deploy command. Do not import a production database, Auth identities, real rosters or storage. Retain the generated staging migration plan and commit SHA with your test notes.

- Apply the 48 repository migrations in chronological order, interleaving one staging-only prerequisite immediately before `20261121090000_vocabulary_afterlight_catalog.sql`. Generate it with `node scripts/staging-reward-prerequisites.mjs`. It emits existing repository wallet and sandbox SQL, the existing five-slot constraint update, and then the original seed. The order allows the original badge seed after the badge category becomes legal. Keep this prerequisite in the disposable staging migration plan and out of the production migration directory. For a linked CLI workflow, generate a temporary migration in the isolated staging checkout dated between the preceding migration and Afterlight, inspect `supabase db push --dry-run`, then use the linked staging project. Record the prerequisite locally and avoid reapplying it to a populated database.
- Seed the public Unit 2 catalogue with `node scripts/export-vocabulary-sql.mjs content/vocabulary/releases/unit-02.js`. Strip the printed `---BEGIN/END VOCAB SQL CHUNK …---` separator lines before execution. Generate Unit 2 Set rows via `membershipSql(membershipRowsForUnit(2))` exported by `scripts/generate-set-membership-sql.mjs`. Compare all six pathway Set counts against the release before browser testing. Seed the app rows from `supabase/seed.sql` after replacing live launch URLs with staging equivalents and retain only the local apps supported by the bundle.
- Create staging accounts through Auth Admin or the staging dashboard first. Associate each returned UUID with a `profiles` row and use synthetic email addresses and one-off test passwords. Create two synthetic classes and the relevant teacher grants. Include active enrolled and uncovered students, an inactive student, a reset-required student, a teacher, an administrator, and a transfer case. Exercise normal class transfer and check the historical membership boundary. The pilot window table must be empty at baseline.
- Deploy only the required staging functions, starting with disabled `active-learning-ingest`, `vocabulary-attempt-action`, `vocabulary-diagnostic` and the functions used by the synthetic access flows. Seed a legitimate staging NGSL completion through the genuine API where the gate requires it. Verify actual missions and attempts on the staged app. Verify project key injection and the deployed JWT mode using staging sessions and the server authentication path. Keep Supabase Auth, PostgREST, and private RPC grants intact. No external integrations should receive staging traffic.

A PostgreSQL 17.12 rehearsal with native Supabase Auth migrations successfully applied all 48 files with the prerequisite sequence and verified the pilot roster was empty. The same rehearsal imported the Unit 2 curriculum and 260 Set memberships across all six pathways. The unaugmented chronological replay fails at Afterlight because the historical reward schema is outside `supabase/migrations`. Applying the historical wallet file in one pass also fails because its badge seed precedes the five-slot constraint update. These findings concern fresh bootstrap only.

## Microsoft sign-in

Use an IT-approved staging-only Entra app registration and a dedicated test identity. Register the **Web** redirect `https://<staging-project-ref>.supabase.co/auth/v1/callback` in that app. In staging Supabase Azure provider settings, configure that application's client ID and secret, and the intended tenant URL `https://login.microsoftonline.com/<tenant-id>`. In Supabase URL Configuration, set the staging Site URL and allow exactly `<staging-site-base>/microsoft-sign-in.html`. The real values depend on the assigned staging project and frontend URL. Azure provider and OAuth redirects belong to staging only.

An Entra administrator is needed if tenant policy restricts app registration, assignment or consent. Ask IT to preassign the synthetic identity to the staging app. For student-path parity, IT must provide an approved **synthetic** identity under the existing school domain. The Hub's existing student checks require that domain, verified email and an approved staging Auth UUID. A synthetic admin can separately exercise the admin sign-in path. Provision and verify the initial matching staging Auth account and profile, configure the existing before-user-created hook in staging, and seed only that synthetic UUID and email in the staging Microsoft allowlist. Inject the Entra secret through the staging dashboard or a secure secret store. Publish a staging-only build with `HUB_STAGING_MICROSOFT=true`. Use the genuine Microsoft session, confirm the expected UUID, exercise an enrolled student's Vocabulary timing, and read credited segments. Production Entra app, provider settings, callback and identity assignments require no changes.

[Supabase Microsoft provider instructions](https://supabase.com/docs/guides/auth/social-sign-in/auth-azure)

## Verify, enroll and reset

- With both staging gates off, verify existing access and a disabled ingest response with zero writes. Enable the server gate only after this baseline. Enroll synthetic students and publish the staging build with `HUB_STAGING_ACTIVE_TIME=true`. Confirm genuine selected and uncovered sessions, managed JWT rejection, transfer attribution, durable retries and the credited-segments RPC. Run real mission completion, drag, recovery, tab and account lifecycle cases. Run sustained traffic only within the staging plan limits. Report request class, latency, stored and credited totals and coverage. Do not log tokens, request content or raw student UUIDs. No managed request throttling or monitoring has been configured yet.
- For the eventual class pilot, preview an approved class's active student roster with completed password setup and export only the UUID snapshot to a restricted operational location. Obtain approval for its count and exact Asia/Shanghai start/end. In one transaction, compare the approved UUID set against the current eligible roster and abort on a membership or count discrepancy. Reject duplicate UUIDs and overlapping windows. Insert only those approved `active_learning_v2_pilot_windows` rows. Verify the exact count and boundaries after commit. Keep enrollment history separate from recorded learning time.
- To close an individual window, set its `ends_at` to the confirmed cutoff. To stop globally, disable Edge ingestion first, close affected windows at the cutoff, and restore a browser build with tracking off. Verify no subsequent admissions. Preserve manifests, intervals, coverage history and all legacy evidence. Only delete synthetic data in a verified disposable project.
- For another feature, rebuild the isolated bundle from the new pinned commit. Review migration deltas before applying, recreate synthetic fixtures as needed, and repeat the isolation probe. To restore the baseline, redeploy the prior known staging bundle and leave optional gates off. Rebuild an empty disposable project if a migration reset is needed. Keep production URLs and keys outside all staging configuration.

The production rollout sequence and remaining prerequisites are in [the V2 release runbook](active-learning-v2-release-verification.md).
